validação de 2026-10-21; ver `tarefas/feito.md`, bloco "F3.7 e M3.7".

## Tabela `public.mapas`

| Coluna | Tipo | Nulo | Observação |
|--------|------|------|------------|
Estado **depois da migração** (`migracao_mapas_pk.sql`, passo 6 do PU-DBA). Até ela rodar no
servidor, a tabela continua como em `mapas.sql`: `id` `GENERATED BY DEFAULT`, sem PK, com
possíveis ids repetidos.

| Coluna | Tipo | Nulo | Observação |
|--------|------|------|------------|
| `id` | `int4 GENERATED ALWAYS AS IDENTITY` (início 1, incremento 1, sem ciclo), **PRIMARY KEY `mapas_pkey`** | não | Uma linha por id. Gerado pelo banco nos INSERT de `teste_graphy`/`teste_metry` e no POST da API, que nunca informam `id`. Id explícito só com `OVERRIDING SYSTEM VALUE` (manual, fora da API). O PUT só faz UPDATE pela PK e nunca cria id (D-P3). |
| `graphy` | `public.geography`, sem typmod (srid 0 no catálogo) | sim | Usada pelo `teste_graphy` (SRID 4326 forçado no INSERT) e pela API |
| `metry` | `public.geometry`, sem typmod (2D, srid 0 no catálogo) | sim | Usada pelo `teste_metry` (SRIDs 4326, 4674, 3857 e 31983) e pela API |

- Constraints: `mapas_pkey PRIMARY KEY (id)` e `mapas_nao_vazia CHECK (graphy IS NOT NULL OR
  metry IS NOT NULL)`. O CHECK nasce `NOT VALID` (vale para linhas novas e alteradas) e é
  validado depois, em passo separado (`validar_check_mapas.sql`). Sem triggers.
- O índice `ix_mapas_id`, sugerido antes, fica redundante com a PK. A migração o remove, mas
  só se ele for exatamente um btree simples de `public.mapas(id)`.
- Sem CHECK de SRID. Uma mesma coluna pode ter linhas com SRIDs diferentes (ver
  `teste_metry/README.md`, REC-2). A criação de CHECK com `NOT VALID` é opcional e ficou para o
  DataBrain, sob pedido do usuário.
- Os SRIDs 4326, 4674, 3857 e 31983 existem em `public.spatial_ref_sys`.
- **Guarda de colunas (RP-2, guarda 0.1 do `roles.sql` e guarda 3.2 da migração).** Os scripts
  abortam sem alterar nada se a tabela tiver colunas além de `id`, `graphy` e `metry`, se
  faltar alguma delas ou se os tipos não forem `int4`/`geography`/`geometry`. O motivo: os
  privilégios da `api_mapas_escrita` são por coluna e o SQL W1 a W4 grava uma coluna por vez;
  uma coluna nova (por exemplo `NOT NULL` sem default) quebraria o POST e mudaria o sentido do
  CHECK. Se a tabela mudar, W1 a W4 e o `roles.sql` precisam ser revistos antes.
- **A migração é pré-requisito também da leitura (RS-23).** O GET da API lê com `LIMIT 2`: se
  o id tiver 2 linhas (tabela não migrada), a resposta é 500 com log Error.

### Nota sobre a sequência da identity

A coluna `id` é identity (`GENERATED ALWAYS` depois da migração). O valor é gerado pela
expressão interna da identity, e o PostgreSQL **não** verifica privilégio na sequência ao
fazer isso: basta o `INSERT` na tabela. Por isso **não há GRANT na sequência** para nenhuma
role, nem para a `api_mapas_escrita`, que faz o POST. `USAGE` na sequência só seria
necessário para `serial` ou `DEFAULT nextval()`, o que não é o caso.

- Prova: `prova_identity_sem_usage.sql` (PO3.1, RS-8). Uma role sem privilégio na sequência
  faz INSERT sem id nos modos `BY DEFAULT` e `ALWAYS`. O `nextval` direto é negado. Em
  `ALWAYS`, id explícito sem `OVERRIDING SYSTEM VALUE` falha com `428C9`. Sem `INSERT` na
  coluna `id`, nem com `OVERRIDING` o id entra (`42501`).
- O `roles.sql` (revisão 5) aborta se `id` não for `GENERATED ALWAYS` (guarda C3,
  `attidentity = 'a'`). A conferência 5.6 mostra que as roles não têm privilégio na
  sequência; esse resultado é o esperado. A 5.12 mostra o próximo valor contra o `max(id)`.
- Se alguém inserir com `OVERRIDING SYSTEM VALUE` um id à frente da sequência, o próximo POST
  que chegar nesse valor falha com `23505` em `mapas_pkey` (R-N3), e a API responde 500. Para
  corrigir, rode de novo a migração: o passo 7 faz o `setval` e nunca volta a sequência.
- Um INSERT que falha (por exemplo, por CHECK) também consome um valor da sequência. Lacunas
  nos ids são normais.

## Roles

As três roles têm os mesmos atributos: `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS
NOREPLICATION NOINHERIT`. Elas são criadas **sem senha**, que é definida depois só com
`\password`. Todas recebem `CONNECT` na base `casaos` e `USAGE` (sem `CREATE`) no schema
`public`, e nenhuma tem privilégio na sequência da identity.

### `api_mapas_escrita` (PUT e POST; RP-1, RP-3, revisão 5 / D-N4)

- Os privilégios são **por coluna** e cobrem exatamente o SQL W1 a W4
  (`api_mapas/sql/consultas_referencia.sql`):
  - `SELECT (id, graphy, metry)`: o `WHERE id = @id` do PUT e o `RETURNING id` do POST;
  - `UPDATE (graphy, metry)`: o PUT grava a coluna da rota pela PK;
  - `INSERT (graphy, metry)`: o POST insere só a coluna da rota, **sem `id`**.
  Uma coluna nova na tabela não fica acessível a ela.
- **Sem `INSERT` em `id` (RS-9).** Com `GENERATED ALWAYS` e sem esse privilégio, a role não
  consegue informar id nem com `OVERRIDING SYSTEM VALUE`.
- **Sem `DELETE` (Q4). O U-2 está encerrado.** O PUT só faz UPDATE e nenhum caminho da API
  apaga linha. Limpar ou apagar linhas pela API fica para um pedido futuro. A limpeza de ids
  criados por testes ou pelo Postman está em "Limpeza de ids de teste" abaixo.
- Sem advisory lock: o lock de linha do UPDATE pela PK basta (D-N6). A conferência antiga 5.12
  (advisory locks) saiu do `roles.sql`.
- `client_min_messages = warning` impede que os `NOTICE` do `ST_IsValid` (que citam
  coordenadas do WKT) cheguem ao cliente.
- `search_path = public` (C9) fixa a resolução das funções do PostGIS usadas sem schema em
  W1 a W4. Sem ele, valeria o `search_path` da base (`"$user", public, topology, tiger`).
- Antes do `COMMIT`, a autoconferência 4.5 aborta tudo se os privilégios efetivos de
  `api_mapas_leitura` e `api_mapas_escrita` não forem exatamente esses (inclusive `INSERT` em
  `id` = f e `DELETE` = f). Isso inclui um `GRANT ... TO PUBLIC` em `public.mapas`.
- A API desliga a escrita na subida (R-1, RS-20) se a role conectada for superusuário, tiver
  `BYPASSRLS` ou `CREATEROLE`, tiver `TRUNCATE` ou `DELETE` em `public.mapas`, tiver `INSERT`
  em `id`, for membro de `pg_write_all_data` ou for dona da tabela (`relowner`). Também
  desliga se faltar a PK exata `mapas_pkey` ou se `id` não for `GENERATED ALWAYS`. Desde a
  PO5.C1 (achado 3), também desliga se a role tiver `UPDATE` em `id` (na coluna ou na tabela
  inteira), `CREATEDB`, `REPLICATION` ou for membro de qualquer outra role
  (`pg_auth_members`). Com a escrita desligada, o POST responde 404 e o PUT 405; o GET
  continua. A consulta é a V1 de `consultas_referencia.sql`, com 14 colunas: habilita só
  com as colunas 0 a 7 = `f`, 8 e 9 = `t` e 10 a 13 = `f`.
- Desligar a escrita pelo banco: `ALTER ROLE api_mapas_escrita NOLOGIN PASSWORD NULL;` e
  `pg_terminate_backend` das sessões dela (seção 6 do `roles.sql`).

Observações:
- As configurações de sessão são só defesa em profundidade, porque o cliente pode alterá-las.
  A proteção real vem dos GRANT/REVOKE.
- `spatial_ref_sys`, usada por `ST_Transform`, já tem `SELECT` para PUBLIC na instalação
  padrão do PostGIS. O script confere isso.
- Os `REVOKE` atingem só essas roles. Nunca troque por `FROM PUBLIC`: isso derrubaria o
  CasaOS e os outros apps da base.
- Se uma role tiver membros, configuração em outra base, ou privilégio ou posse fora do
  esperado, o script aborta sem alterar nada. A checagem é feita em `pg_shdepend`. Um `CREATE`
  residual no schema `public` é removido.

## Migração para PRIMARY KEY (PU-DBA; D-N3, RS-10 a RS-14, RS-24)

Pedido de 2026-10-23: `public.mapas.id` passa a ser PRIMARY KEY, `GENERATED ALWAYS`, com uma
linha por id. **Os agentes não executam nada; quem roda é o usuário/DBA**, como `casaos`
(superusuário), por socket local dentro do container. Siga esta ordem (RS-11):

1. **Desligar a escrita antiga.** Remova `PG_ESCRITA_*` da sessão da API e/ou rode:

   ```sql
   ALTER ROLE api_mapas_escrita NOLOGIN PASSWORD NULL;
   SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE usename = 'api_mapas_escrita';
   ```

   A migração aborta se ainda houver sessão da `api_mapas_escrita` (guarda 3.6).
2. **Backup** de `public.mapas` (`backup_mapas.sh --container <container>` ou
   `backup_mapas.ps1`). Confira `Backup OK`, a contagem e o SHA-256. Se falhar, pare.
3. **Relatório** (somente leitura, sem geometria):

   ```bash
   sudo docker exec -i <container> psql -X -v ON_ERROR_STOP=1 -U casaos -d casaos \
        -f - < database/relatorio_duplicados_mapas.sql
   ```

   - **Não salve a saída** no repositório, no OneDrive nem em `tarefas/*.md`. Leia no terminal.
     Se precisar guardar, use `~/backups_postgis` e apague depois da migração (RS-24).
   - Rode como `casaos`. A R2 só é confiável como `casaos`: a `api_mapas_leitura` não tem
     privilégio na sequência, e nesse caso a R2 mostra `sem privilegio` em `last_value` e
     `proximo_valor`, com `r2_confiavel = f` (PO5.C1, achado 5). `nunca usada` em
     `last_value` quer dizer sequência sem nenhum `nextval`.
   - R1 traz o resumo, R2 a sequência, R3 um registro por id duplicado com `mesclavel` ou
     `conflitante`, R4 o detalhe dos conflitantes (ctid, tipo, SRID, pontos e md5) e R5 as
     linhas vazias isoladas.
4. **Deduplicação** com `mescla_duplicados_mapas.sql`. O padrão é **ensaio** (ROLLBACK); só
   grava com `-v confirmar=1`, exatamente. `confirmar=0`, `nao`, `sim`, vazio ou qualquer outro
   valor fazem ROLLBACK, como sem a variável (PO5.C1, achado 4).
   - Mescláveis (parte A), primeiro o ensaio, depois a gravação:

     ```bash
     sed -n 's/^--: //p' database/mescla_duplicados_mapas.sql \
       | sudo docker exec -i <container> psql -X -v ON_ERROR_STOP=1 -U casaos -d casaos -f -
     sed -n 's/^--: //p' database/mescla_duplicados_mapas.sql \
       | sudo docker exec -i <container> psql -X -v ON_ERROR_STOP=1 -v confirmar=1 -U casaos -d casaos -f -
     ```

   - Conflitantes (parte B, um id por vez): o **usuário** escolhe, pela seção R4, de qual linha
     vem o `graphy` e de qual vem o `metry` que ficam (`nenhum` deixa a coluna NULL). O md5 é
     conferido antes de gravar; se o ctid tiver mudado, o script aborta e o relatório deve ser
     rodado de novo:

     ```bash
     sed -n 's/^--c: //p' database/mescla_duplicados_mapas.sql \
       | sudo docker exec -i <container> psql -X -v ON_ERROR_STOP=1 -v id=<id> \
           -v graphy_ctid='(<pagina>,<item>)' -v graphy_md5=<md5> \
           -v metry_ctid=nenhum -v metry_md5=nenhum [-v confirmar=1] \
           -U casaos -d casaos -f -
     ```

   - Rode o relatório de novo: o esperado é `ids_duplicados = 0`.
5. **Segundo backup**, se tiver passado muito tempo desde o primeiro.
6. **Migração**, numa única transação (`-1`), parando no primeiro erro:

   ```bash
   sudo docker exec -i <container> psql -X -v ON_ERROR_STOP=1 -1 -U casaos -d casaos \
        -f - < database/migracao_mapas_pk.sql
   ```

   - Ordem: `lock_timeout` 5s e `statement_timeout` 5min → `LOCK ACCESS EXCLUSIVE` → guardas
     (colunas, tipos, identity, PK/UNIQUE/índice único, CHECK, sessões da escrita) → contagem →
     id NULL/duplicado → PK `mapas_pkey` → `setval` → `GENERATED ALWAYS` → CHECK `NOT VALID` →
     `DROP INDEX` restrito → conferência → `COMMIT` (feito pelo `-1`).
   - Qualquer erro faz ROLLBACK de tudo. As mensagens trazem só contagens e no máximo 20 ids.
   - É idempotente: rodar de novo só mostra `pulado`.
   - O `setval` nunca volta a sequência. A migração aborta se `max(id) > 2147483647 - 1000000`.
   - A tabela fica travada (leitura e escrita) só durante a transação.
7. **`VALIDATE` do CHECK**, depois de o relatório mostrar `linhas_vazias = 0`. As linhas vazias
   restantes são decisão do usuário (apagar ou preencher):

   ```bash
   sudo docker exec -i <container> psql -X -v ON_ERROR_STOP=1 -1 -U casaos -d casaos \
        -f - < database/validar_check_mapas.sql
   ```

## SSL do servidor (ação 5 / S-3)

Situação atual: `ssl = off`, `password_encryption = scram-sha-256`, PG 17.x no container
Docker do CasaOS em 192.168.168.106. A seção 7 do `roles.sql` (revisão 3, ainda não executada)
liga o SSL **sem restart**, porque desde o PG 10 `ssl` e os arquivos de certificado mudam com
`pg_reload_conf()`.

**Configurações aplicadas por `ALTER SYSTEM`** (gravadas em `postgresql.auto.conf`, fora de
transação, depois do `COMMIT` das roles):

| Parâmetro | Valor |
|-----------|-------|
| `ssl` | `on` |
| `ssl_cert_file` | `server.crt` (relativo ao `data_directory`, volume persistente) |
| `ssl_key_file` | `server.key` |
| `ssl_min_protocol_version` | `TLSv1.2` (mínimo mantido por compatibilidade com o Npgsql no Windows) |
| `ssl_ciphers` | `HIGH:!aNULL:!eNULL:!MD5:!3DES:!RC4` (vale para TLS 1.2; o TLS 1.3 usa as suítes padrão) |

**Certificado** (`gerar_certificado_ssl.sh`, roda no host do servidor, `set -euo pipefail`):
- CA própria (10 anos) e certificado de servidor assinado por ela (825 dias), ECDSA P-256 por
  padrão ou RSA 3072 com `--rsa`. SAN `IP:<ip>` (padrão 192.168.168.106) e, opcionalmente,
  `DNS:<hostname>` com `--dns`.
- A CA tem `nameConstraints` crítico: só pode emitir para o IP do servidor (máscara
  255.255.255.255, ou /128 no IPv6) e, com `--dns`, para esse hostname.
- Gerado com `umask 077` em `~/pg_ssl`, ou em `--out-dir`. O script recusa diretórios dentro
  do OneDrive (componente `OneDrive` ou `OneDrive - <org>` no caminho) ou de um repositório git.
  Também recusa diretório que não pertença ao usuário que executa. O `openssl` roda no host
  com uma configuração mínima própria (`OPENSSL_CONF`), sem depender do `openssl.cnf` global.
  O do Git for Windows, por exemplo, quebra o `req -x509`.
- Copia `server.crt` (0644) e `server.key` (0600) com `docker cp` e ajusta o dono para o dono
  do `data_directory` (usuário `postgres`) via `docker exec -u root`.
- Não sobrescreve um certificado já existente no container sem `--force`. Com `--force`, os
  arquivos antigos são renomeados no container para `.bak.<data>`, mantendo o dono e com a
  chave em 0600.
- Se `ca.key` e `ca.crt` já existirem no diretório, a CA é reutilizada, depois de conferir que
  o par corresponde, e os clientes continuam válidos. Se existir só um dos dois, ou se o par não
  corresponder, o script aborta antes de gerar qualquer coisa.
- `ca.key` **nunca** vai para o container. Guarde-a em lugar seguro, fora do OneDrive e do
  repositório. `ca.crt` vai para os clientes que usarem `VerifyFull`.
- **NÃO importe o `ca.crt` no repositório de certificados do Windows nem do sistema; use-o só
  via `sslrootcert` / parâmetro de CA do cliente.**

**Proteções da seção 7:**
- Antes do `ALTER SYSTEM`, a guarda 7.1 aborta se `server.crt` ou `server.key` não existirem
  no `data_directory` (`pg_stat_file`), se estiverem vazios, se não forem PEM, se a chave
  estiver cifrada (PKCS#8 cifrado ou PEM tradicional com `Proc-Type: 4,ENCRYPTED`) ou se o
  processo `postgres` não conseguir lê-la. Também aborta se
  `ssl_ca_file`/`ssl_crl_file` apontarem para arquivo inexistente. Motivo: com `ssl = on`
  gravado e o arquivo ausente ou ilegível, **o servidor não sobe no próximo restart**.
- Se a seção 7 abortar, as roles já estão gravadas e o SSL continua como estava.

**Conferência depois do reload:**
- `SHOW ssl` (esperado `on`), `pg_settings` dos parâmetros `ssl%` (inclusive `ssl_ciphers`,
  com `pending_restart = f`) e `pg_file_settings` sem erro.
- `SHOW ssl = on` **não prova** que o certificado carregou. Se o carregamento falhar, o PG
  registra o erro no log e não aceita SSL. Os dois testes abaixo são **OBRIGATÓRIOS, logo
  depois** do script:
  - `sudo docker logs --since 5m <container> 2>&1 | grep -i -E 'ssl|certif|private key'`;
  - uma conexão TCP real com `sslmode=require`. A senha é digitada no prompt do `psql`; nunca
    use `PGPASSWORD=...` nem senha na linha de comando:

    ```bash
    sudo docker exec -it <container> psql \
        "host=localhost dbname=casaos user=casaos sslmode=require" \
        -c "SELECT ssl, version FROM pg_stat_ssl WHERE pid = pg_backend_pid();"
    ```

    O esperado é `t` e TLSv1.2 ou 1.3. Depois do `\password`, repita da máquina cliente com
    `host=192.168.168.106 user=mapas_teste`.
- **Se algum dos dois falhar: rollback imediato, antes de qualquer restart do container.**

  ```sql
  ALTER SYSTEM RESET ssl;
  ALTER SYSTEM RESET ssl_cert_file;
  ALTER SYSTEM RESET ssl_key_file;
  ALTER SYSTEM RESET ssl_min_protocol_version;
  ALTER SYSTEM RESET ssl_ciphers;
  SELECT pg_reload_conf();
  SHOW ssl;   -- esperado: off
  ```

  Corrija os arquivos (`--force`) e repita a seção 7.

**SSL ligado não é SSL obrigatório.** Sem `hostssl` + `reject` no `pg_hba.conf` (passo 5), um
cliente com `sslmode=Disable`/`Prefer` continua entrando sem criptografia. Conexões por
socket local (`docker exec ... psql`) não usam SSL.

**Clientes:** `PG_SSLMODE=Require` criptografa, mas não valida o certificado. `VerifyFull`
valida a cadeia e o IP/hostname, e exige que o cliente confie no `ca.crt`. Os programas
(`teste_graphy`, `teste_metry`, `api_mapas`) hoje não têm variável própria para o caminho da
CA. Isso é pendência de backend, a ser pedida pelo analista.

Os agentes não executam estes passos. Use sempre placeholders (`<container>`, `<IP>`) e

3. **Rodar o script** como superusuário, por socket local dentro do container:

   Em seguida, é **OBRIGATÓRIO** conferir a seção 7 (SSL), o `docker logs` e a conexão TCP com


   ```sql
   \password api_mapas_leitura
   ```
