# Manual da base de dados — PostGis_poc

Servidor 192.168.168.106, base `casaos`, PostgreSQL 17 com PostGIS 3.5.2. Os dados vêm da
validação de 2026-10-21; ver `tarefas/feito.md`, bloco "F3.7 e M3.7".

Arquivos desta pasta:

| Arquivo | Conteúdo |
|---------|----------|
| `mapas.sql` | DDL de origem da tabela `public.mapas`. Não é executada pelos programas. |
| `roles.sql` | Criação e ajuste das roles `mapas_teste` e `api_mapas_leitura`. É a **fonte oficial** das roles, aprovada pelo SecBrain. A seção 7 liga o SSL do servidor. |
| `gerar_certificado_ssl.sh` | Gera a CA e o certificado do servidor no host e copia `server.crt`/`server.key` para o `data_directory` do container. Rodado pelo DBA antes do `roles.sql`. |

Nenhum arquivo desta pasta contém senha ou chave privada.

## Tabela `public.mapas`

| Coluna | Tipo | Nulo | Observação |
|--------|------|------|------------|
| `id` | `int4 GENERATED BY DEFAULT AS IDENTITY` (início 1, incremento 1, sem ciclo) | não | Gerado pelo banco. Os programas nunca informam `id`. |
| `graphy` | `public.geography`, sem typmod (srid 0 no catálogo) | sim | Usada pelo `teste_graphy` (SRID 4326 forçado no INSERT) e pela API |
| `metry` | `public.geometry`, sem typmod (2D, srid 0 no catálogo) | sim | Usada pelo `teste_metry` (SRIDs 4326, 4674, 3857 e 31983) e pela API |

- Sem PK, sem `UNIQUE` em `id`, sem constraints e sem triggers. Antes de criar PK/UNIQUE,
  verificar se há `id` duplicado (S-5, ação 6 do DBA).
- Sem CHECK de SRID. Uma mesma coluna pode ter linhas com SRIDs diferentes (ver
  `teste_metry/README.md`, REC-2). A criação de CHECK com `NOT VALID` é opcional e ficou para o
  DataBrain, sob pedido do usuário.
- Os SRIDs 4326, 4674, 3857 e 31983 existem em `public.spatial_ref_sys`.

### Nota sobre a sequência da identity

A coluna `id` é `GENERATED BY DEFAULT AS IDENTITY`. O valor é gerado pela expressão interna da
identity, e o PostgreSQL **não** verifica privilégio na sequência ao fazer isso: basta o
`INSERT` na tabela. Por isso **não há GRANT na sequência** para nenhuma role. `USAGE` na
sequência só seria necessário para `serial` ou `DEFAULT nextval()`, o que não é o caso.

O script `roles.sql` aborta se `id` deixar de ser identity (guarda C3). A conferência 5.6 do
script mostra que as roles não têm `USAGE` na sequência; esse resultado é o esperado.

## Roles

As duas roles têm os mesmos atributos: `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS
NOREPLICATION NOINHERIT`. Elas são criadas **sem senha**, que é definida depois só com
`\password`. As duas recebem `CONNECT` na base `casaos` e `USAGE` (sem `CREATE`) no schema
`public`.

| | `mapas_teste` | `api_mapas_leitura` |
|---|---|---|
| Uso | Testes de integração F6.6 (`teste_graphy`) e M6.6 (`teste_metry`) | API `api_mapas` (A7.3) |
| `public.mapas` | `SELECT`, `DELETE`, e `INSERT` só nas colunas `graphy` e `metry` | só `SELECT` |
| Negado | `INSERT` informando `id`, `UPDATE`, `TRUNCATE`, `CREATE` | `INSERT`, `UPDATE`, `DELETE`, `CREATE` |
| `CONNECTION LIMIT` | 5 | 20 (igual ao `Maximum Pool Size` da API) |
| Sessão | `statement_timeout` 30s, `lock_timeout` 10s, `idle_in_transaction_session_timeout` 60s | `default_transaction_read_only` on, `statement_timeout` 15s, `idle_in_transaction_session_timeout` 60s |

Observações:
- As configurações de sessão são só defesa em profundidade, porque o cliente pode alterá-las.
  A proteção real vem dos GRANT/REVOKE.
- `spatial_ref_sys`, usada por `ST_Transform`, já tem `SELECT` para PUBLIC na instalação
  padrão do PostGIS. O script confere isso.
- Os `REVOKE` atingem só essas roles. Nunca troque por `FROM PUBLIC`: isso derrubaria o
  CasaOS e os outros apps da base.
- Se uma role tiver membros, configuração em outra base, ou privilégio ou posse fora do
  esperado, o script aborta sem alterar nada. A checagem é feita em `pg_shdepend`. Um `CREATE`
  residual no schema `public` é removido.

**Validação local (sessão principal, PostGIS 17.5/3.5 descartável no Docker):**
- O script rodou duas vezes sem erro (é idempotente).
- `mapas_teste` fez INSERT em `graphy`/`metry` com `RETURNING id`, SELECT e DELETE em
  transação. Foi negado ao informar `id` e ao fazer UPDATE.
- `api_mapas_leitura` fez SELECT e `ST_Transform`. INSERT e CREATE foram negados.
- Um GRANT extra fez o script abortar.

## SSL do servidor (ação 5 / S-3)

Situação atual: `ssl = off`, `password_encryption = scram-sha-256`, PG 17.x no container
Docker do CasaOS em 192.168.168.106. A seção 7 do `roles.sql` (revisão 3, ainda não executada)
liga o SSL **sem restart**, porque desde o PG 10 `ssl` e os arquivos de certificado mudam com
`pg_reload_conf()`.

**Configurações aplicadas por `ALTER SYSTEM`** (gravadas em `postgresql.auto.conf`, fora de
transação, depois do `COMMIT` das roles):

| Parâmetro | Valor |
|-----------|-------|
| `ssl` | `on` |
| `ssl_cert_file` | `server.crt` (relativo ao `data_directory`, volume persistente) |
| `ssl_key_file` | `server.key` |
| `ssl_min_protocol_version` | `TLSv1.2` (mínimo mantido por compatibilidade com o Npgsql no Windows) |
| `ssl_ciphers` | `HIGH:!aNULL:!eNULL:!MD5:!3DES:!RC4` (vale para TLS 1.2; o TLS 1.3 usa as suítes padrão) |

**Certificado** (`gerar_certificado_ssl.sh`, roda no host do servidor, `set -euo pipefail`):
- CA própria (10 anos) e certificado de servidor assinado por ela (825 dias), ECDSA P-256 por
  padrão ou RSA 3072 com `--rsa`. SAN `IP:<ip>` (padrão 192.168.168.106) e, opcionalmente,
  `DNS:<hostname>` com `--dns`.
- A CA tem `nameConstraints` crítico: só pode emitir para o IP do servidor (máscara
  255.255.255.255, ou /128 no IPv6) e, com `--dns`, para esse hostname.
- Gerado com `umask 077` em `~/pg_ssl`, ou em `--out-dir`. O script recusa diretórios dentro
  do OneDrive (componente `OneDrive` ou `OneDrive - <org>` no caminho) ou de um repositório git.
  Também recusa diretório que não pertença ao usuário que executa. O `openssl` roda no host
  com uma configuração mínima própria (`OPENSSL_CONF`), sem depender do `openssl.cnf` global.
  O do Git for Windows, por exemplo, quebra o `req -x509`.
- Copia `server.crt` (0644) e `server.key` (0600) com `docker cp` e ajusta o dono para o dono
  do `data_directory` (usuário `postgres`) via `docker exec -u root`.
- Não sobrescreve um certificado já existente no container sem `--force`. Com `--force`, os
  arquivos antigos são renomeados no container para `.bak.<data>`, mantendo o dono e com a
  chave em 0600.
- Se `ca.key` e `ca.crt` já existirem no diretório, a CA é reutilizada, depois de conferir que
  o par corresponde, e os clientes continuam válidos. Se existir só um dos dois, ou se o par não
  corresponder, o script aborta antes de gerar qualquer coisa.
- `ca.key` **nunca** vai para o container. Guarde-a em lugar seguro, fora do OneDrive e do
  repositório. `ca.crt` vai para os clientes que usarem `VerifyFull`.
- **NÃO importe o `ca.crt` no repositório de certificados do Windows nem do sistema; use-o só
  via `sslrootcert` / parâmetro de CA do cliente.**

**Proteções da seção 7:**
- Antes do `ALTER SYSTEM`, a guarda 7.1 aborta se `server.crt` ou `server.key` não existirem
  no `data_directory` (`pg_stat_file`), se estiverem vazios, se não forem PEM, se a chave
  estiver cifrada (PKCS#8 cifrado ou PEM tradicional com `Proc-Type: 4,ENCRYPTED`) ou se o
  processo `postgres` não conseguir lê-la. Também aborta se
  `ssl_ca_file`/`ssl_crl_file` apontarem para arquivo inexistente. Motivo: com `ssl = on`
  gravado e o arquivo ausente ou ilegível, **o servidor não sobe no próximo restart**.
- Se a seção 7 abortar, as roles já estão gravadas e o SSL continua como estava.

**Conferência depois do reload:**
- `SHOW ssl` (esperado `on`), `pg_settings` dos parâmetros `ssl%` (inclusive `ssl_ciphers`,
  com `pending_restart = f`) e `pg_file_settings` sem erro.
- `SHOW ssl = on` **não prova** que o certificado carregou. Se o carregamento falhar, o PG
  registra o erro no log e não aceita SSL. Os dois testes abaixo são **OBRIGATÓRIOS, logo
  depois** do script:
  - `sudo docker logs --since 5m <container> 2>&1 | grep -i -E 'ssl|certif|private key'`;
  - uma conexão TCP real com `sslmode=require`. A senha é digitada no prompt do `psql`; nunca
    use `PGPASSWORD=...` nem senha na linha de comando:

    ```bash
    sudo docker exec -it <container> psql \
        "host=localhost dbname=casaos user=casaos sslmode=require" \
        -c "SELECT ssl, version FROM pg_stat_ssl WHERE pid = pg_backend_pid();"
    ```

    O esperado é `t` e TLSv1.2 ou 1.3. Depois do `\password`, repita da máquina cliente com
    `host=192.168.168.106 user=mapas_teste`.
- **Se algum dos dois falhar: rollback imediato, antes de qualquer restart do container.**

  ```sql
  ALTER SYSTEM RESET ssl;
  ALTER SYSTEM RESET ssl_cert_file;
  ALTER SYSTEM RESET ssl_key_file;
  ALTER SYSTEM RESET ssl_min_protocol_version;
  ALTER SYSTEM RESET ssl_ciphers;
  SELECT pg_reload_conf();
  SHOW ssl;   -- esperado: off
  ```

  Corrija os arquivos (`--force`) e repita a seção 7.

**SSL ligado não é SSL obrigatório.** Sem `hostssl` + `reject` no `pg_hba.conf` (passo 5), um
cliente com `sslmode=Disable`/`Prefer` continua entrando sem criptografia. Conexões por
socket local (`docker exec ... psql`) não usam SSL.

**Clientes:** `PG_SSLMODE=Require` criptografa, mas não valida o certificado. `VerifyFull`
valida a cadeia e o IP/hostname, e exige que o cliente confie no `ca.crt`. Os programas
(`teste_graphy`, `teste_metry`, `api_mapas`) hoje não têm variável própria para o caminho da
CA. Isso é pendência de backend, a ser pedida pelo analista.

## Procedimento de execução (DBA, nesta ordem)

Os agentes não executam estes passos. Use sempre placeholders (`<container>`, `<IP>`) e
nunca grave senhas em arquivo.

1. **Backup de `public.mapas`**, fora do repositório e fora do OneDrive:

   ```bash
   umask 077; mkdir -p ~/backups_postgis
   sudo docker exec <container> pg_dump -U casaos -d casaos -t public.mapas \
       > ~/backups_postgis/mapas_backup_AAAAMMDD.sql
   grep -c '^COPY public.mapas' ~/backups_postgis/mapas_backup_AAAAMMDD.sql   # esperado: 1
   ```

2. **Gerar e instalar o certificado** no host do servidor:

   ```bash
   bash database/gerar_certificado_ssl.sh --container <container> [--ip 192.168.168.106] [--dns <host>]
   ```

   Use `sudo` ou `DOCKER="sudo docker"` se o usuário não estiver no grupo docker. Guarde o
   `ca.key` em lugar seguro.

3. **Rodar o script** como superusuário, por socket local dentro do container:

   ```bash
   sudo docker exec -i <container> psql -U casaos -d casaos < database/roles.sql
   ```

   Confira as consultas da seção 5 do script. O esperado é `CREATE` no schema `public` = `f`.
   Em seguida, é **OBRIGATÓRIO** conferir a seção 7 (SSL), o `docker logs` e a conexão TCP com
   `sslmode=require` (ver "Conferência depois do reload"). Se falhar, faça o rollback
   imediatamente, antes de qualquer restart do container.

4. **Definir as senhas**, só no `psql` interativo:

   ```bash
   sudo docker exec -it <container> psql -U casaos -d casaos
   ```

   ```sql
   SHOW password_encryption;   -- esperado: scram-sha-256
   \password mapas_teste
   \password api_mapas_leitura
   ```

   Regras: 16+ caracteres aleatórios, diferentes entre si e da senha de `casaos`.

5. **Ajustar o `pg_hba.conf`** com as linhas abaixo **antes** da linha genérica
   `host all all all scram-sha-256`. Com o SSL ligado, a liberação é `hostssl`, e os `reject`
   barram as tentativas sem SSL:

   ```
   hostssl  casaos  mapas_teste,api_mapas_leitura  <IP>/32  scram-sha-256
   host     all     mapas_teste,api_mapas_leitura  0.0.0.0/0  reject
   host     all     mapas_teste,api_mapas_leitura  ::/0       reject
   ```

   - Enquanto o SSL não estiver confirmado, a liberação pode ficar como `host` (só na exceção
     formal `PG_SSLMODE=Disable`).
   - Com Docker, o `client_addr` pode ser o gateway da bridge. Confira em `pg_stat_activity`
     antes de fixar o `/32`, e não alargue a máscara.
   - Depois de editar: `SELECT pg_reload_conf();` e `SELECT * FROM pg_hba_file_rules;` (a
     coluna `error` deve ficar vazia).
   - Atenção: a imagem oficial do Postgres traz `local all all trust`, o que permite entrar por
     socket dentro do container sem senha. Esse risco foi aceito, porque exige acesso ao
     container.

6. **Clientes** com `PG_SSLMODE=Require`, ou `VerifyFull` quando o cliente confiar no
   `ca.crt`.

## Pós-teste (depois que F6.6 e M6.6 passarem)

Opção preferida: desativar o login, apagar a senha e derrubar as sessões abertas.

```sql
ALTER ROLE mapas_teste NOLOGIN PASSWORD NULL;
SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE usename = 'mapas_teste';
```

Alternativa, que mantém a role ativa sem poder apagar dados:
`REVOKE DELETE ON public.mapas FROM mapas_teste;`.

Para uma nova rodada de testes, rode `roles.sql` de novo (ele reaplica `LOGIN` e os GRANTs) e
defina uma senha **nova** com `\password mapas_teste`.
